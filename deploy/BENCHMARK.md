# Порівняння одного й двох воркерів

9 листопада 2026 року надіслано однакову партію з трьох синтетичних MP4 через DRF API. Ролики містили мовлення, мали роздільність 720p і частоту 24 кадри за секунду. Порядок подачі в обох прогонах становив 105, 60 і 35 секунд.

| Показник | Один воркер | Два воркери |
| --- | ---: | ---: |
| Завершення всієї партії | 98,11 с | 56,49 с |
| Середнє очікування в черзі | 41,93 с | 12,22 с |
| Максимальне очікування в черзі | 80,95 с | 35,93 с |
| Завершено на Ubuntu (`node-1`) | 3 | 2 |
| Завершено на Kali (`node-2`) | 0 | 1 |

Із двома воркерами партія завершилася у **1,74 раза швидше**, а середнє очікування скоротилося на **70,9%**. Перші два завдання оброблялися одночасно приблизно 35,5 с.

| Відео | Вузол з одним воркером | Черга / обробка | Вузол з двома воркерами | Черга / обробка |
| --- | --- | ---: | --- | ---: |
| 105 с | `node-1` | 0,71 / 43,44 с | `node-2` | 0,53 / 47,30 с |
| 60 с | `node-1` | 44,13 / 36,87 с | `node-1` | 0,19 / 35,79 с |
| 35 с | `node-1` | 80,95 / 17,03 с | `node-1` | 35,93 / 20,44 с |

Ubuntu й Kali працювали в Parallels на одному Mac, по два vCPU на VM і по одному процесу Celery для відео. Використано Whisper `tiny` на CPU. Перед замірами обидва вузли обробили по одному 35-секундному ролику для прогріву й початкової оцінки швидкості. Вимірювані партії починали з порожніх черг і тих самих даних прогріву. У першому прогоні воркер Kali був зупинений. Обидва прогони виконано в тимчасовому стенді з окремою базою, Redis і каталогом медіа.

Час партії виміряно від створення першої задачі в API до завершення останньої. Очікування окремої задачі виміряно від її створення до початку обробки. Шість задач завершилися успішно, API повернув посилання на SRT і MP4 для кожної. Це по одному прогону на конфігурацію. Результати залежать від роликів і ресурсів хоста. Прогони використовували ту саму формулу прогнозу. У фінальному коді диспетчер читає чергу та активні роботи одним запитом до БД, щоб завдання, яке саме переходить із черги в обробку, не випало з підрахунку.

## Повторення

На окремому тестовому розгортанні підготуйте три ролики й токен staff-акаунта в змінній `TITRY_BENCHMARK_TOKEN`. Дочекайтеся порожньої черги. Для першого прогона залиште доступним лише `node-1`. Потім запустіть `node-2`, дочекайтеся heartbeat і повторіть запит з тими самими файлами. Для HTTPS із локальним CA передайте шлях до сертифіката через `--ca`.

```bash
python deploy/benchmark.py --url "$TITRY_URL" --ca "$TITRY_CA" \
    --workers node-1 -- clip-105s.mp4 clip-60s.mp4 clip-35s.mp4 > one-worker.json

python deploy/benchmark.py --url "$TITRY_URL" --ca "$TITRY_CA" \
    --workers node-1 node-2 -- clip-105s.mp4 clip-60s.mp4 clip-35s.mp4 > two-workers.json
```

Сценарій використовує ті самі запити завантаження і статусу, що й колекція Postman. JSON містить метрики партії, UUID, вузол і часові позначки для кожної задачі.
